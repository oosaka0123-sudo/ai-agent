# 開発ルール

このドキュメントは、人間・AIエージェント（Claude Code / Codex / Gemini など）を問わず、
このリポジトリで開発する際に守るべきルールをまとめたものです。

## 1. ブランチ運用

- `main` ブランチには直接pushしない。常にPull Requestを経由する。
- 作業ブランチは用途がわかる名前をつける。
  - 例: `feature/news-collector`, `fix/env-loading-bug`, `docs/update-readme`
- `main` は常にビルド・起動できる状態を維持する（壊れた状態でマージしない）。

## 2. コミットメッセージ

- 1コミット1目的を基本とする。
- 「何を」「なぜ」変更したかが分かるように書く。
  - 良い例: `ニュース取得APIのタイムアウトを30秒に延長`
  - 悪い例: `修正`, `update`

## 3. Pull Request のルール

- PRを出す際は `.github/pull_request_template.md` に従って記載する。
- 動作確認した内容、秘密情報を含んでいないことを必ずチェックする。
- 可能な限り小さい単位でPRを分割する（レビューしやすくするため）。
- CI（`.github/workflows/ci.yml`）が失敗している状態でマージしない。

## 4. 秘密情報の管理（最重要）

- APIキー・パスワード・トークンなどは **絶対に** コードやコミットに含めない。
- 秘密情報は `.env` に記載し、`.gitignore` で除外する（設定済み）。
- 新しい環境変数を追加したら、`.env.example` にキー名だけを追記する（値は空欄）。
- もし誤って秘密情報をコミットしてしまった場合:
  1. 直ちにそのAPIキー・トークンを発行元サービスで無効化・再発行する。
  2. リポジトリ管理者に報告する。
  3. 履歴からの削除（`git filter-repo` 等）が必要か判断する。

## 5. 複数AIエージェントが並行して作業する場合の注意

- 作業前に必ず最新の `main` を取得する（`git fetch` / `git pull`）。
- 他のエージェント・人間と同じファイルを同時に大きく変更しそうな場合は、
  作業範囲を分ける、またはIssue/PRで作業内容を明示する。
- push前にコンフリクトがないか確認し、あれば解消してからpushする。
- 生成したコードは必ず内容を確認してからコミットする（意味のわからないコードを
  そのままコミットしない）。

## 6. コーディング規約

言語・フレームワークは本プロジェクトではまだ確定していません。
機能追加のタイミングで採用した言語ごとに、以下を決めてこのセクションに追記してください。

- フォーマッタ / リンターの設定
- ディレクトリ内でのファイル命名規則
- テストの書き方・実行コマンド

## 7. CI/CD

- `.github/workflows/ci.yml` に土台を用意しています（現時点ではシークレットスキャンのみ）。
- 言語・フレームワークが決まったら、lint・テスト・ビルドのステップを追加してください。
- 可能であれば、GitHubリポジトリ設定で `main` ブランチにブランチ保護ルールを設定し、
  「CIが通過しないとマージできない」「レビュー必須」などを有効にしてください
  （この設定はリポジトリ管理者がGitHub上のSettingsから行う必要があります）。
