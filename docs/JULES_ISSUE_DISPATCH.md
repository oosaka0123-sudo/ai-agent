# GitHub Issue経由 Jules正式発注フロー

本ドキュメントは、GitHub Issueを司令塔の発注口とし、Julesへ自律実装を依頼する正式運用フローの正本です。

## 1. 概要

- **発注口**: GitHub Issue
- **トリガー**: Issueに `jules` ラベルを付与する（またはIssueテンプレート「Jules Task」で作成する）
- **対象AI**: Jules
- **基本原則**: JulesはIssueの本文を作業指示書として受け取り、専用の作業ブランチ上で自律的に実装・検証・PR作成まで行います。

---

## 2. 正式発注フローのステップ

```
[人間/スマホ] Issue作成（julesラベル）
       │
       ▼
[Jules] Issue本文を取得し専用ブランチを作成
       │
       ▼
[Jules] 実装 → テスト/検証 → 自己レビュー → 修正 → 再テスト
       │
       ▼
[Jules] Pull Requestを作成（テスト・検証結果を記載）
       │
       ▼
[GitHub Actions] 既存Copilot自動レビューが発動
       │
       ▼
[Copilot] 変更内容をレビュー
  ├─ 変更要求あり ──> [Jules] 修正コミット → 再レビュー依頼
  └─ 承認/コメント ─> 人間へ通知
       │
       ▼
[人間] PRを確認し最終マージ判断（自動マージ禁止）
```

### ステップ詳細

1. **Issue起票 (スマホ対応)**
   - ユーザーは `.github/ISSUE_TEMPLATE/jules-task.md` テンプレートを使用してIssueを作成します。
   - `jules` ラベルが付与された時点で、Julesへの正式作業依頼となります。
2. **作業開始 & ブランチ作成**
   - Julesは `main` ブランチに直接pushせず、必ず目的がわかる専用作業ブランチ（例: `jules/feature-xxx`, `jules/fix-xxx`）を作成して作業します。
3. **自律実行サイクル (実装 → テスト → 自己レビュー → 修正 → 再テスト)**
   - Julesは `AGENTS.md` の自律実行ルールに従い、途中で不要な確認を挟まず最後まで作業を完遂します。
   - コード変更後は必ずローカル環境で検証・テストを実施します。
4. **Pull Requestの作成**
   - 完遂条件を満たした後、Julesは Pull Request を作成します。
   - PR本文には、具体的に実施した**テスト/検証内容**、および自己評価を明確に記載します。
5. **Copilot自動レビューとの連携**
   - PR作成後、既存の `.github/workflows/copilot-auto-review.yml` により GitHub Copilot が自動レビューを実行します。
   - Copilot から修正要求（`Changes required`）が出された場合、Jules はその指摘事項を分析し、修正コミットを行って再レビューを依頼します。
6. **人間による最終マージ判断**
   - 最終マージは必ず**人間の判断**で行います。自動マージは無効化・禁止とします。

---

## 3. 安全ルール・禁止事項

1. **`main` 直pushの禁止**: 作業はすべて専用ブランチで行うこと。
2. **自動マージの禁止**: コミット・PR作成まではAIが自律で行うが、`main` へのマージボタンを押すのは人間のみ。
3. **担当外ファイルの無関係な変更の禁止**: 他AIの担当ファイルや不要なスコープに影響を与えないこと。
4. **Secrets / 権限設定の変更禁止**: リポジトリ設定、Workflow権限、Secrets等を変更しないこと。

---

## 4. Julesへの発注テンプレート

新しい作業を依頼する際は、`.github/ISSUE_TEMPLATE/jules-task.md` を利用してください。
スマホ（画面幅390px程度）から短時間で入力できるように設計されています。

- **目的**: 何のために何をするか
- **変更対象**: どのファイル・機能を変更するか
- **完了条件**: どうなったら完成か
- **触ってはいけない範囲**: 変更してはならないコードやファイル
- **確認/テスト方法**: どのように動作確認するか
