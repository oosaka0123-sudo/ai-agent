## 共有ナビの aria-current 二重付与バグを修正（追記）

- プロジェクト: AIエージェント

### 今日やったこと

- 上記の仕上げ作業を自己レビューする過程で、`web/assets/js/render.js` の共有ナビ生成処理
  （`initSiteNav`）を静的にコードトレースし、`web/guides/index.html` を開いたときに
  「HOME」と「ガイド」の2つのナビ項目が同時に `aria-current="page"` になるバグを発見した。

  区別できていなかったこと。
- `initSiteNav` の現在地判定を、ベース名比較から `new URL(href, location.href).pathname` による
  フルパス比較に変更して修正した。

## PR #67マージ前QA: モバイル横スクロール実バグの発見・修正（追記）

- プロジェクト: AIエージェント

### 今日やったこと

- PR #67（CIはコミット82f55fbで成功済み）のマージ前QAとして、Chrome DevTools Protocolで
  390 CSSピクセル幅（`Emulation.setDeviceMetricsOverride`で`mobile:true`指定）を正確に
  エミュレーションし、全9ページ×2ビューポート（390px/1280px）で
  `document.documentElement.scrollWidth` と `clientWidth` を実測した。
- モバイル幅で全ページ共通して `scrollWidth`（約700）が `clientWidth`（390）を大きく超過している
  実バグを発見した。原因は、閉じた状態のモバイル用ドロワーナビ（`.topbar-nav`、
  `position:fixed;right:0;transform:translateX(100%)`で画面外へ退避させる実装）が、
  視覚的には見えないにもかかわらず、`position:fixed`要素のレイアウト上の占有領域として
  ページ全体の横スクロール可能領域を310px分（ドロワー幅）広げていたため。
  `body`には既に`overflow-x:hidden`が設定済みだったが、`position:fixed`要素の
  スクロール可能領域への寄与はhtml/bodyの`overflow`設定では抑制できないことを、
  実際にCDPで複数のアプローチ（`overflow-x:hidden`のみ／`overflow-x:clip`／
  `right`オフセットへの置き換え等）を1つずつ試して確認した。
- 併せて、`.timeline-card-desc`等のカード説明文に空白を含まない長い技術文字列
  （URLやトークン等）を注入する実験を行い、`overflow-wrap`未設定のテキスト要素と
  `min-width`未設定のグリッド/フレックスアイテムが、ページの横スクロールを
  誘発しうることも実証した（実データでは現状顕在化していないが、将来の長い文字列で
  再発しうる潜在バグとして修正対象に含めた）。

### 発見した問題（実測で確認済み）

1. モバイル幅で、ドロワーナビが閉じている状態でも `document.documentElement.scrollWidth`
   が `clientWidth` を約310px超過していた（全ページ共通、`web/assets/js/render.js`の
   共有ナビCSSが原因）。
2. カード・タイムライン・ガイドテーマカード・Markdown本文中のテキストに、空白を含まない
   長い技術文字列が入ると、グリッド/フレックスアイテムの既定の `min-width:auto` により
   ページの横スクロールが発生しうる状態だった（`web/assets/css/style.css`）。

### 修正した内容

- `web/assets/js/render.js`: `.topbar-nav`のモバイル用オフキャンバス表現を、
  `transform:translateX(100%)`（要素をビューポート外へ物理的に移動）から、
  要素自体は常に`right:0`でビューポート内に置いたまま`clip-path:inset(0 0 0 100%)`で
  表示範囲だけを切り替える方式に変更した。これにより、閉じた状態でも要素の
  レイアウト境界がビューポート内に収まり、ページの横スクロール領域を広げなくなる。
  開閉のトランジション・キーボード操作（Escape）・背景クリック・リンククリックでの
  クローズ・フォーカス復帰など、既存の挙動はすべて維持した。
- `web/assets/css/style.css`: `html`にも`body`と同様の`overflow-x`（`hidden`を
  フォールバックとしつつ対応ブラウザでは`overflow-x:clip`）を追加。加えて、
  `.card` / `.timeline-card` / `.theme-card`（グリッド・フレックスアイテム）に
  `min-width:0`を、`.card-title` / `.card-sub` / `.timeline-card-title` /
  `.timeline-card-desc` / `.theme-card-title` / `.theme-card-desc` /
  `.detail-panel p,li` / `.markdown-body p,li,code` に `overflow-wrap:anywhere`
  （`code`要素はさらに`word-break:break-all`）を追加し、長い技術文字列がカード幅・
  ページ幅を押し広げないようにした。

### 学んだこと（技術的な知見）

- `position:fixed`要素は、たとえ`transform`で画面外へ退避させて視覚的に見えなくても、
  そのレイアウト境界がビューポート（初期包含ブロック）を超えていれば、ページ全体の
  横スクロール可能領域（`document.documentElement.scrollWidth`）を押し広げる。
  `html`/`body`の`overflow-x:hidden`や`overflow-x:clip`はこれを抑制できない
  （`position:fixed`要素の包含ブロックはビューポートそのものであり、祖先要素の
  `overflow`によるクリッピングの対象にならないため）。オフキャンバスUIを実装する際は、
  要素自体をビューポート外に移動させる（`transform`や`right`のマイナスオフセット等）
  のではなく、要素の位置は常にビューポート内に固定したまま`clip-path`等で
  表示/非表示を切り替える方が、この種の不具合を根本から避けられる。
- CDPで`Network.setCacheDisabled`を呼ぶ場合、事前に`Network.enable`を呼んでいないと
  設定が効かず、同一オリジンへの再アクセス時に古い（編集前の）CSS/JSがキャッシュから
  返り続けることがある。今回の調査中、この呼び出し順序の誤りにより「CSSを修正しても
  ブラウザ上で反映されない」という誤った現象に一時遭遇し、原因切り分けに時間を要した。
  今後同種のCDP実測を行う際は、`Network.enable`→`Network.setCacheDisabled(true)`の順で
  呼び出し、可能であればキャッシュバスティングも併用して確認する。
