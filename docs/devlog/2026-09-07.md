## Steel Browser MCP — GitHub WIFによる自動デプロイと実受入

### OBSERVED

- Steel Browser MCPのCloud Runは`/readyz -> {"ready":true}`まで稼働済み。
- PR #57でGitHub OIDC専用`POST /acceptance`と、Secret値を返さない実5工程acceptance runnerをmainへ追加した。
- PR #57のCIはGitleaks成功、152 tests PASS、shell構文チェック成功。
- PR #57 merge後も本番Cloud Runは旧revisionのままで、`GET /acceptance`が旧middlewareの`{"error":"unauthorized"}`を返したため、新しいacceptanceコード未デプロイと判定した。
- ChatGPTのOpera Browser ConnectorはCloud Shell画面を読めるがterminalへtype/Enterできず、Cloud Shell helper起動が最後の人手ゲートとして残っていた。

### IMPLEMENTATION

- `.github/workflows/steel-browser-acceptance.yml`を、受入だけでなくSteel productionの自動deployも行うworkflowへ拡張した。
- mainのSteel関連ファイル変更時または`workflow_dispatch`時に、GitHub Actions OIDC + Google Cloud Workload Identity Federationで短期認証する。
- 長期GCPサービスアカウント鍵をGitHub Secretsへ保存しない。
- GitHub runnerで`Dockerfile.steel-browser`をbuildし、Artifact Registryへcommit SHA tagでpushした後、既存Cloud Run serviceのimageだけを更新する。既存Secret/env/runtime service account設定を上書きしない。
- deploy後に`/readyz`を確認し、別のGitHub OIDC tokenで`POST /acceptance`を実行する。
- application acceptance側はrepository/ref/workflow_refに加え、`push`または`workflow_dispatch`のみ許可する。
- `scripts/bootstrap_steel_github_wif.sh`を追加。GCP側のWIF trust、専用deployer SA、最小deploy権限を一度だけ構成し、その場で現行mainの再デプロイと実5工程受入まで行う。
- `scripts/redeploy_steel_browser_mcp.sh`を手動fallback兼bootstrap内の初回deploy helperとして追加。
- `gha-creds-*.json`を`.gitignore`と`.dockerignore`の双方で除外し、一時OIDC credentialsがcommitやcontainer build contextへ入らないようにした。

### SECURITY

GitHub deployer SAへ付与する権限は次に限定する。

- Project: `roles/run.developer`
- Project: `roles/serviceusage.serviceUsageConsumer`
- Artifact Registry repository: `roles/artifactregistry.writer`
- Steel runtime SA: `roles/iam.serviceAccountUser`
- GitHub WIF principal: deployer SAに対する`roles/iam.workloadIdentityUser`

WIF provider自体も`oosaka0123-sudo/ai-agent`、`refs/heads/main`、固定workflow_ref、`push|workflow_dispatch`条件でfail-closedにする。

### REMAINING EXTERNAL BOUNDARY

GCP側がGitHubを信頼するWIF設定だけは、GCP認証済み主体が一度作成する必要がある。merge後にCloud Shellで`bootstrap_steel_github_wif.sh`を1回起動すれば、WIF構成 -> Steel再デプロイ -> 実5工程受入まで連続実行できる。その後のSteel変更はGitHub Actionsで自動deploy/acceptanceへ移行する。
