## この方法の特徴

スマホのブラウザ、GitHub、AIとのチャットを組み合わせ、**ファイル作成から公開までをスマホだけで完結**させる方法です。最初はビルド作業が不要な `index.html` と `style.css` の2ファイルから始めます。仕組みが単純なので、問題が起きても原因を切り分けやすく、初心者の最初の1ページに向いています。

このガイドでは、AIに完成品を丸投げするのではなく、「要件を伝える → 小さな変更を受け取る → 内容を確認する → GitHubへ保存する」を繰り返します。AIの回答は必ずプレビューし、秘密情報や意図しないコードがないことを確認してから保存します。

## 必要なサービス

- **GitHubアカウント**: HTMLやCSSの保存、変更履歴の管理、GitHub Pagesでの公開に使います。
- **AIを利用できるチャットまたはコーディング環境**: Codexなどに設計、コード作成、修正案を依頼します。
- **スマホのブラウザ**: GitHubと公開ページを操作します。標準ブラウザで構いません。
- **テキストを一時保存できるメモアプリ**: 長いコードの受け渡しや、公開前のバックアップに役立ちます。

GitHubのリポジトリは公開設定でも秘密情報を置いてはいけません。APIキー、パスワード、個人情報をHTMLやJavaScriptへ書かないでください。

## スマホでの手順

- 作りたいページの目的、対象読者、掲載内容、色、必要なボタンをメモします。
- GitHubで新しいリポジトリを作り、`index.html` と `style.css` を追加します。
- AIへ要件と制約を伝え、まず最小構成のコードを作ってもらいます。
- GitHub上でコードを各ファイルへ貼り付け、変更内容が分かるメッセージでコミットします。
- GitHub Pagesを有効にし、発行されたURLをスマホで開きます。
- 縦向きと横向きで、文字、リンク、ボタン、画像、横スクロールの有無を確認します。
- 問題を具体的にAIへ伝え、1回に1種類ずつ修正して再確認します。

最初から多機能にせず、「見出し・説明・リンク」だけで公開成功を確認してから画像やJavaScriptを足すと、安全に進められます。

## GitHubリポジトリ作成

GitHubへサインインし、新規リポジトリを作成します。名前は半角英数字とハイフンを使った短いもの、たとえば `my-first-site` にするとURLが分かりやすくなります。GitHub Pagesで一般公開する前提なら公開範囲も確認してください。

最初にREADMEを追加しておくと、リポジトリの目的や編集方法を残せます。作成後はファイル追加機能で `index.html` を作ります。ファイル名は半角小文字で正確に入力し、`Index.html` や `index.htm` との取り違えを避けます。続けて `style.css` を追加します。

編集のたびに、`トップページの土台を追加` や `スマホ用の余白を調整` のような、変更内容が分かるコミットメッセージを付けます。正常だった時点へ戻りやすくするため、変更は小分けに保存します。

## AIとの接続

利用中のCodex環境にGitHub連携機能がある場合は、画面の案内に従って対象リポジトリだけを許可します。権限の範囲、対象ブランチ、提案された差分を毎回確認し、`main` を直接変更せず作業ブランチとPull Requestを使うと安全です。画面や契約によって連携機能が使えない場合でも、チャットでコードを受け取り、GitHubの編集画面へ貼り付ける方法で進められます。

依頼文には次の情報をまとめます。

- サイトの目的と対象読者
- 必要な文章、セクション、リンク
- 希望する色や雰囲気
- スマホ幅を優先すること
- HTML、CSS、必要最小限のJavaScriptだけを使うこと
- 外部ライブラリを使うかどうか
- 変更するファイル名と、今回変更しない範囲

たとえば「`index.html` と `style.css` を分け、幅390pxでも横スクロールが出ず、見出し構造とフォーカス表示を備えた1ページを作ってください」のように、確認可能な条件で頼みます。エラーを相談するときは「動かない」だけでなく、URL、操作手順、期待した結果、実際の結果、表示されたメッセージを共有します。ただしトークンなどの秘密情報は送らないでください。

## HTML/CSS作成

`index.html` にはページの意味と内容、`style.css` には見た目を記述します。最初のHTMLでは `lang="ja"`、文字コード、viewport設定、ページタイトルを用意し、`header`、`main`、`section`、`footer` など内容に合う要素を使います。画像には内容を伝える代替テキストを付け、リンクやボタンは指で押しやすい大きさと間隔にします。

CSSはスマホ向けの基本スタイルから書き、画面が広い場合だけメディアクエリで調整します。固定幅を多用せず、`max-width`、パーセント、折り返しを利用します。本文の文字を小さくしすぎず、文字色と背景色のコントラスト、キーボード操作時のフォーカス表示も確認します。

JavaScriptは必要になってから追加します。問い合わせフォームのように受信先やサーバー処理が必要な機能は、HTMLだけでは完成しません。最初はメールリンクや信頼できるフォームサービスへのリンクなど、仕組みを理解できる代替案を検討します。

## GitHubへの保存

保存前に、AIが提示したコードを最初から読みます。特に外部URL、読み込むスクリプト、フォームの送信先、追跡コード、秘密情報らしい文字列を確認します。変更箇所だけでなくファイル全体を見て、以前の内容が消えていないかも確認します。

作業ブランチを作れる場合は、そこで編集してPull Requestを作ります。差分表示で追加行と削除行を確認し、公開ページをテストしてから既定ブランチへ反映します。小さなサイトでもこの流れを使うと、AIの提案を人が確認した履歴を残せます。

画像はリポジトリ内の `assets/` などへ置き、HTMLから相対パスで参照します。大きすぎる画像は表示を遅くするため、適切な寸法とWeb向け形式へ最適化します。ファイル名の大文字と小文字は公開環境で区別されることがあるので、参照と完全に一致させます。

## 公開方法

リポジトリのGitHub Pages設定を開き、案内に従って公開元を選びます。単純な静的サイトなら、公開するブランチとルートフォルダを指定する方式が分かりやすいです。設定画面の名称は更新されることがあるため、現在表示されているGitHubの説明を優先してください。

公開処理には少し時間がかかる場合があります。表示された公開URLを開き、トップページだけでなく全リンクをタップします。更新が見えないときは、処理状況、公開元のブランチ、`index.html` の場所、ファイル名、ブラウザの再読み込みを順に確認します。

GitHub Pagesは静的ファイルの公開に適していますが、サーバー上で秘密のキーを使う処理、データベース、ログイン処理をHTMLだけで安全に実現することはできません。そのような機能は、別途バックエンドや適切なサービスを設計します。

## 初心者が迷いやすい点

- **公開URLとリポジトリURLは別**: コードを見る場所と、完成ページを見る場所を区別します。
- **反映に時間差がある**: コミット直後に古い表示でも、すぐに同じ変更を繰り返さず処理状況を確認します。
- **ファイルの場所が違う**: 公開元に指定した場所へ `index.html` があるか確認します。
- **相対パスが合わない**: `style.css` や画像のパスは、HTMLファイルから見た位置で書きます。
- **大文字・小文字が違う**: `Photo.webp` と `photo.webp` を同じものとして扱わないよう統一します。
- **AIのコードを一度に全部交換する**: 動いている箇所まで壊さないよう、変更対象と理由を限定します。
- **秘密情報を公開する**: ブラウザへ送られるHTML、CSS、JavaScriptから秘密を隠すことはできません。

## メリット

- PCが手元になくても、思いついた内容をすぐページにできます。
- GitHubのコミット履歴により、変更内容を追跡しやすくなります。
- GitHub Pagesなら静的サイトを簡単に共有できます。
- AIへ文章整理、コード作成、原因調査を相談でき、学習の入口を作れます。
- HTMLとCSSの基本を保ったまま始めるため、後から別の環境へ移しやすいです。

## デメリット

- スマホでは長いコードの選択、比較、複数ファイルの編集が難しくなります。
- AIは誤ったコードや不要な処理を提案することがあり、人による確認が必要です。
- 無料枠、利用制限、GitHub Pagesの仕様は各サービスの変更を受けます。
- 静的サイトだけでは、秘密情報を使うAPI処理や本格的な会員機能を実装できません。
- 端末やブラウザが1種類だけだと、他の環境での表示不具合を見逃しやすくなります。

## 費用

基本的な公開サイトは、GitHubとGitHub Pagesの利用条件内で無料から始められます。AIサービスは無料枠、定額プラン、従量課金などがあり、利用する環境で異なります。独自ドメインを使う場合はドメインの取得・更新費用が別途必要です。フォーム、アクセス解析、画像配信など外部サービスを追加すると料金が発生する場合があります。

料金や無料枠は変わるため、登録前に各サービスの公式料金ページと利用条件を確認します。最初は追加課金のない最小構成で公開し、必要性が明確になってから有料機能を選ぶのがおすすめです。

## PCが必要か

1ページの静的サイトを作成・修正・公開する範囲なら、PCは必須ではありません。スマホだけで一連の流れを経験できます。

ただし、ファイル数が増えた開発、大きな差分のレビュー、自動テスト、画像の細かな加工、複数ブラウザでの検証ではPCの方が効率的です。「スマホだけで開始できる」と「どんな規模でもスマホだけが最適」は別です。作業が複雑になった時点でPCやタブレットを併用して構いません。

## 最終的に何ができるか

自己紹介、活動案内、店舗やイベントの告知、作品集、リンク集などの静的なホームページを、スマホから作成してURLで共有できます。GitHubにはソースコードと変更履歴が残るため、あとから文章やデザインを更新できます。

さらに、独自ドメイン、フォーム、アクセス解析、PWAなどへ段階的に発展させられます。その際も、まず目的とデータの扱いを確認し、機能を小さく追加し、スマホ表示・アクセシビリティ・セキュリティを再テストする流れを続けます。
